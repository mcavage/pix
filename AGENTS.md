# AGENTS.md: pix

You're working on **pix**: a personal, multi-model **pi** coding-agent
harness that runs inside **Docker Sandboxes** (`sbx`) on a **DHI** (Docker
Hardened Image) Node/Debian base. You may be *running inside* a pix sandbox
or *editing this repo* to extend the harness. This file is the harness's memory:
read it before changing things, and keep it current as you learn.

## Build → load → run (read this before iterating)

- **Image or baked files** (Dockerfile, settings, keybindings, agents/skills/extensions/themes) → `make load` (build + `docker save` + `sbx template load`). The sbx runtime has its **own image store**, so a locally-built image MUST be loaded in: otherwise sbx pulls it from the registry. `make load` is **heavy** (~1GB tar); batch changes.
  - **The image tag MUST be pinned (never `:latest`).** Docker re-pulls `:latest` on every run even when the image is already loaded, so `make load` gets ignored and you keep downloading. A pinned tag (`VERSION` in the Makefile = `image:` in `pi-kit/spec.yaml` = `version` in package.json) gets IfNotPresent semantics: use the loaded build if present, else pull once.
  - **You (the agent) CANNOT run `make load` / `make run` from inside a pix sandbox**: they need the **host's** Docker + `sbx` CLI, which the VM has no access to. Don't offer to. Edit the baked files, sync them into the live `~/.pi/agent/...` dir + `/reload` for the current session, and tell the **user** to run `make load` on their host to bake it for future sandboxes.
- **Kit only** (`pi-kit/spec.yaml`) → just `make run` a fresh sandbox. `--kit` applies at sandbox **creation** only: no rebuild needed.
- **Skills load in one of two modes, decided by the entry point.** `make run` and `pix run --dev` are **Mode B (dev):** skills load LIVE from the host tree (`--no-skills --skill <repo>/skills`; a pack adds its own `skills/` on top via `pix pack use`), so editing a `SKILL.md` on the host + `/reload` (or a fresh `make run`) is instant: **no `make load`, no image rebuild.** A consumer's `sbx run --kit git+…` (or `pix` without `--dev`) is **Mode A (baked):** the skills compiled into the image. So for your own skill iteration, edit the mounted source and `/reload`; `make load` is only for baking your skills into the image for *consumers*/publish.
- **This file** (`AGENTS.md`) and other workspace files are read live from the mount: no rebuild.
- A running sandbox keeps its **creation-time image**; recreate (`sbx rm -f … && make run`) to pick up image changes.
- **Testing:** never create/remove a sandbox named `pix-pix`: that's what `make run` uses, so you'll collide and strand sbx state. Use `--name pix-test`.
- **Load-check an extension without keys:** `docker run --rm docker.io/mcavage/pix:$(VERSION) bash -lc 'pi -p hi'` → "No API key" means extensions loaded fine; "Failed to load extension …" means fix it before loading.

## Updating pi (mechanical, don't relearn)

pi is pinned via `ARG PI_PACKAGE=@earendil-works/pi-coding-agent@<version>` in the Dockerfile. The in-sandbox "Update available" banner just means a newer point release shipped (pi checks npm at runtime); it returns on every release, so bump intentionally. To bump:

1. **Find the target version:** `npm view @earendil-works/pi-coding-agent version` (latest), or pick a specific one from `npm view @earendil-works/pi-coding-agent versions`.
2. **Edit the `PI_PACKAGE` ARG** in the Dockerfile to `@earendil-works/pi-coding-agent@<version>`. Changing the ARG busts the pi-install layer so the rebuild actually reinstalls.
3. **`make load`** (rebuild + load).
4. **Verify the vendored patches still apply.** tui is non-fatal: the log must show `[apply-tui-bottom-pin] patched`, not `anchor not found`; if it warns, refresh `tui-bottom-pin.block.txt` + the anchor (renderer = `dist/tui-main-screen.js` since pi-tui 0.84, `dist/tui.js` before; the script tries both). **pi-web-access is fatal-on-mismatch and fails the build**: dry-run `PI_WEB_ACCESS_DIR=<pkg> node scripts/patches/apply-web-access-gateway.mjs` before re-pinning it (held at 0.13.0 on purpose: 0.19.0 upstreamed our seams under other key names).
5. **Verify the version:** `docker run --rm --entrypoint pi docker.io/mcavage/pix:$(VERSION) --version`.
6. **Recreate sandboxes** to pick up the new pi (they keep their creation-time image): `sbx rm -f <name>` then re-run. A stale sandbox is also the usual cause of in-sandbox auth 401s and "missing extension" surprises, since it carries old image + proxy wiring.

### Safety invariants (never relearn these, never violate them)

These are the properties that cost real incidents to discover. They are load-bearing, they are asserted by `tests/agents-md-invariants.test.mjs`, and each is a behavior you must preserve, not prose you may summarize away.

1. `~/.config/pix/config.toml` is the SINGLE runtime config and is managed by `pix config set`/`unset` (never hand-edit it). `Save()` persists only explicit deviations from defaults, so a future default change still reaches users.
2. **An implicit launch requires a TTY.** Bare `pix` IS `pix run` here (attach if the sandbox is up, else create), as is `pix DIR` for an existing dir. Both being implicit, both gate on interactive stdin: non-interactive, bare `pix` degrades to read-only status and `pix DIR` refuses (stderr, exit 2). No script or pipe may launch as a side effect. Explicit `pix run` is never gated.
3. **`serve stop` is mode-aware.** A managed daemon (launchd/systemd --user) is stopped THROUGH its supervisor, never by a bare pid SIGTERM: `KeepAlive`/`Restart=` respawns it instantly, which is the classic "I stopped it but it came right back" bug.
4. **Serve runtime state lives in the STATE dir** (`~/.local/state/pix/`: `serve.pid`, `serve.lazy`, `serve.spawn.lock`, `serve.log`), not the config dir, so moving the config dir aside can never orphan a running daemon from its pidfile.
5. **Direct provider keys come from 1Password only.** `op` is REQUIRED only for the direct-API-key path; missing or not-signed-in is a HARD failure there. Keyless `sbx-session`, `none`, and verified Ollama backends never trigger an irrelevant 1Password flow.
6. **`run` refuses to launch only on a POSITIVE "no model key" answer.** The key probe is tri-state; a transient `sbx secret ls` failure proceeds. A false refusal is worse than a failed launch.
7. **An existing sandbox is never force-removed and never replayed into.** `--replace` is DELETED (it forced a removal with no zero-holder proof); recreating is a proof-gated `pix rm BOX`, then `pix run`. The one forced seam is a named `pix rm --force`; the same non-force teardown also fires when the last interactive shell exits. `--keep`/`-k` (with `--all`) spares named sandboxes from bulk removal; `--orphans` sweeps zero-reference sandboxes with no keep hold (hard-crash recovery). Sandbox state sbx could not report (unknown) FAILS CLOSED. `sbx` v0.38 makes `-f` a CONFIRMATION bypass, not an authority bypass: `sandbox.PlanForceRemove` (same pix-* scope check as `PlanRemove`) composes it for the proof-gated seams above AND the explicit `--force` one; see `docs/upstream/sbx-0.38-noninteractive-rm.md`.
8. **Pack trust is two gates in series with `host.enabled`.** Adopting a pack that runs host code (local MCP command, host wrapper, external `[[bin]]`) hits a Tier-1 bill-of-materials gate (`[y/N]`; non-TTY fails closed without `--yes`). Acceptance lives in a launcher-owned host-state store, NEVER in the pack payload. A canonical host-exec fingerprint re-gates on any change. Unknown local-vs-remote MCP classification fails CLOSED. Credentials are `op://` refs only.
9. **Host mode is DELETED, not merely off by default.** The unsandboxed `pix host` escape hatch and the credential-broker plugin slot were removed outright (`host.enabled` gates no code path at all) so the sandbox is the only supported mode. `pix host` is simply not a verb: it gets the ordinary unknown-command answer, because pix has no released users to keep a recovery path for.
10. **`pix secret` never writes a secret value to disk**: it only seeds, opens, and validates the `op://` refs file. Values stay in 1Password.
11. **`pix rm` is scoped to `pix-*` sandboxes only.** It can never reach a sandbox it did not create.
12. **Success words are earned by a probe.** `ready`/`verified` only after a post-mutation check; never print `configured`/`enabled` as a success verdict.

## go-plugin + Suture host architecture

`pix-host serve` is a **Suture v4** supervision tree over **go-plugin** subprocess units. Suture owns restart/backoff policy; `services/host/supervise/` owns what Suture cannot know (go-plugin handshake, health identity, reattach-across-restart). **memory** (:11435) ALWAYS runs as a supervised go-plugin unit: the built-in impl is a self-exec of the same binary (`pix-host plugin memory`); a `[plugins.memory]` block in `config.toml` (`path`, `sha` SHA-pinned, `port`) overrides it with an external, signed subprocess instead. `serve` itself keeps owning the stable :11435 listener (`memoryProxyMux`) so the child can restart/reattach underneath it without the sandbox noticing. There is NO monitor: the whole subsystem (in-sandbox tap, ingest listener, store, reader verb) was removed; see `docs/design/monitor.md` for what went and why. Every ACTIVE pack's Tier-1-accepted `[[services]]` entries are reconciled into the SAME supervision tree at `serve` startup (`sup.reconcilePackUnits`) as their own go-plugin units: a bad pack's load/trust failure only logs, it never blocks `serve` or a sibling pack.

**Knowledge (:11436) and the credential-broker plugin slot are DELETED, not merely retired-from-the-CLI.** No `config.toml` key, no supervised unit, no code path dispenses either: `hostmode_gone_test.go` is a permanent grep-based sentinel against either symbol set ever coming back. The `knowledge` capability in `capabilities.json` defaults to `none` in the public stack; a private pack wires a `files` or `http` provider directly (not through `pix-host serve`).

## Writing extensions (`extensions/*.ts`)

- Shape: `export default function (pi: any) { … }`. pi loads `.ts` **directly** (no build step), with **full Node globals at runtime**: `process`, `require`, `setInterval` all work. `@types/node` + `tsconfig.json` make tsserver/`tsc` recognize them. **Do NOT "fix" `process`/`require` errors by deleting them**: they're real at runtime; it was only a type-lint gap (now configured).
- An extension that throws **at load breaks pi startup** → guard defensively. Prefer a commented `catch { /* best-effort; must not break the agent */ }` over an empty one, or actually handle it.
- **`/reload` hangs are almost always a factory that never returns.** pi awaits each extension factory on reload, so any unsettled `await` at load (classically `await server.listen(port)` that hits EADDRINUSE because the pre-reload instance still holds the port, with no `error` handler) wedges the whole reload. Settle the promise on BOTH `listening` and `error`, and close listeners on `session_shutdown`. See `extensions/ollama-bridge.ts`.
- Core API: `pi.registerCommand(name, {description, handler})`, `pi.registerShortcut("ctrl+alt+x", {…})`, `pi.on(event, (e, ctx) => …)`, `pi.registerTool(…)`, `pi.events`. In handlers: `ctx.ui.notify / setWorkingMessage / setStatus / setWidget`, `ctx.model`, `ctx.getContextUsage()`, `ctx.abort()`, `ctx.isIdle()`.
- Useful events: `turn_start` / `turn_end`, `tool_execution_start` / `update` / `end`, `message_update`, `before_provider_request` / `after_provider_response`, `tool_call` (return `{block,reason}` to gate), `session_shutdown`.
- `extensions/status.ts` is the canonical defensive pattern (live working-line + `/status` + stall watchdog).
- **Never put `.d.ts` (or any non-extension `.ts`) in `extensions/`**: pi tries to load *every* `.ts` there as an extension factory and **crashes pi startup** on a declaration file (`does not export a valid factory function`). Put ambient types in `types/` (covered by `tsconfig` `include`); Node globals come from `@types/node`.
- **Display-only injected messages:** `pi.sendMessage` defaults to `deliverAs:"steer"`, which **triggers an LLM call to deliver the message**. Fired from an idle hook (e.g. `agent_end`) it ends the conversation on an assistant turn, and reasoning models (`claude-opus-4-8`) **400 with "assistant prefill not supported"**. For pure display annotations use `deliverAs:"nextTurn"` ("does not interrupt or trigger anything") and strip them in the `context` hook by `customType`. See `extensions/timestamps.ts`.
  - **Exception, and it is load-bearing: never strip `pix-recalled-context` or `pix-output-style`.** Both are delivered as append-only `before_agent_start` messages, and removing an already-sent message moves the provider's prefix-cache divergence point BACKWARDS: strictly worse than the system-prompt rewrite they avoid. Enforced by `scripts/check-recall-transport.sh` and `tests/recall-context-hook.test.mjs`.

## Writing skills (`skills/<name>/SKILL.md`)

YAML frontmatter `name` + `description` (when to use), then tight markdown steps.
Auto-discovered; invoke `/skill:<name>` or let it auto-load. Delegate heavy or
parallel work with the `subagent` tool (single / parallel / chain / trees), naming
an agent from `agents/` (e.g. `fanout`, `review`, `deep`), see the subagents note
under “Models & subagents”. (Older skills say the `Agent` tool with
`subagent_type=…`; that API is not present: use `subagent` with `agent=…`.)

A skill is **pure mechanism**: never bake one person's specifics (their channels,
accounts, names, thresholds) into a SKILL.md. Those are per-user and live in
**memory** (the skill reads them at runtime); the skill only knows the *shape*.

**Improving a pack skill: edit the pack's source on the host.** A pack's `skills/`
dir lives in the pack repo on the host (e.g. `~/dev/work-pack/skills/<name>/`)
and is mounted at runtime by `pix pack use` (no image bake, no rebuild). The
copy pi loaded this session (`~/.pi/agent/skills/<name>/SKILL.md`) is a read-only
delivery that dies with the sandbox; edits there are lost. So when you improve a
pack skill mid-session, write the change to the **pack repo's** source on the
host; it's live on the next `/reload` or fresh run (packs mount at launch, so
there is nothing to `make load`). From inside a sandbox you can't reach the host
pack repo: hand the user the diff to apply.

## Models & subagents

- Providers: **Claude, GPT, Gemini** (proxy-injected cloud keys) plus **Ollama** through its local daemon (local or Cloud). Switch `/model`; **Alt+P** cycles.
- **ALWAYS fully-qualify model ids** (`provider/id`); bare names may resolve to a keyless provider and hang. Current registry: `anthropic/claude-{opus-5,fable-5,sonnet-5,haiku-4-5}`, `openai/gpt-5.6-{sol,terra}`, `google/gemini-{3.1-pro-preview,3.7-flash,3.1-flash-lite}`, `ollama/{qwen3.5:9b,glm-5.2:cloud,kimi-k3:cloud}`. - Preset roles resolve THROUGH the router by intent (see `pix agent ls` for the live map + a WHY for each pick), not hard-coded models: `fanout` = intent `breadth` (→ Gemini Flash-Lite, cheap read-only breadth), `review` = intent `review` (→ Gemini 3.1 Pro, cross-vendor adversary), `deep` = intent `max-accuracy` (→ Opus 5, the one hard problem: Fable is reserved for security). The writer crew (`ux-copywriter`/`devrel`/`growth-marketing`/`enrich`) = intent `writing` (→ Gemini Flash, off-Anthropic since Claude is the weak writer). Change the resolved model by editing `policy.json`/`scorecard.json` and running the `model-refresh` skill, not the agent.
- **Top-level session model** is the `overlord` intent (→ GPT-5.6 Sol), the SHIPPED `run_intent` default (`config.DefaultRunIntent`). `run.go` defaults `--intent` from `config.run_intent` when neither `--model` nor `--intent` is passed; a bad value degrades to pi's default rather than blocking launch. Change it with `pix config set run_intent <intent>` (e.g. `strategy` for Opus on an Anthropic-only host); `run_intent none` opts out to pi's own default model; `unset` restores `overlord`. `doctor` warns when the resolved intent's provider key is missing. The orchestrator is pinned OFF Anthropic on purpose. NOTE: the default assumes an OpenAI key is present.
- **Model routing + agent lifecycle (cost/latency/accuracy).** Agents are first-class objects but the CLI facet is **read-only**: `pix agent ls` shows each agent's RESOLVED model and WHY (an agent is a hand-edited `agents/*.md` plus `make routing`, never a CLI mutation). An agent declares an **`intent:`** (`overlord`, `max-accuracy`, `strategy`, `code`, `advisory`, `writing`, `reasoning`, `review`, `red-team`, `breadth`, `verify`, `authoring`, `fast-balanced`), NOT a pinned model. Posture, **tiered by leverage**: **Opus 5** for expensive-to-get-wrong work (`strategy`/`advisory`/`max-accuracy`/`authoring`); **Sonnet 5** the `code` workhorse; **Fable 5** reserved for the one frontier role that earns it, `red-team`; and deliberate cross-vendor roles OFF Anthropic: `overlord` → GPT-5.6 Sol, `writing` → Gemini Flash, `review` → Gemini 3.1 Pro; cheap/high-volume `breadth`/`verify` → Gemini Flash-Lite/Flash. An intent is a **hard-constraint problem**: filter by cost/latency ceilings + accuracy floor, then optimize the objective. `prefer_providers` is a **preference, not an allowlist**: an unwired vendor is silently skipped, so **every intent needs a cost ceiling or its fallback lands on the most expensive model in the catalog** (that is how `overlord` once defaulted to Fable 5; `routing/overlord_fallback_test.go` pins it). A genuinely hard vendor rule belongs in `inference.exclusive_backend`, at the binding layer. Truth lives on the HOST (Go, `services/host/routing/`): `models.json` (registry + limits + prices: adding a model is ONE entry), `scorecard.json` (**hand-maintained**, seeded from published benchmarks: no eval harness measures them), `policy.json` (the intents). `make routing` compiles every intent into **`routing.json`**, read **offline** by `subagents.ts`. Explicit `model:` wins; unknown intent degrades to "inherit parent". Sessions route too: `pix run --intent code`. Wire a provider: `pix models add <provider>`; `pix models ls` marks `wired`/`unwired`/`retired`. Full design: `docs/design/routing.md`.
- **Subagents are BACK, via our own `extensions/subagents.ts`** (replaces the off-the-shelf `@tintinweb/pi-subagents`, which deadlocked: see `docs/design/subagents-extension.md`). It registers a `subagent` tool with **single / parallel / chain** modes and depth-capped **trees**. Call it with `{agent, task}` (single), `{tasks:[...]}` (parallel), or `{chain:[...]}` with a `{previous}` placeholder: agent = a filename in `agents/`. It spawns each child as `pi --no-extensions -e <inference> -e <self>`: the curated inference extension restores generated gateway providers, while avoiding a full extension load because that re-binds ollama/memory ports and hangs. An inactivity + wall-clock **watchdog** ensures a stuck child is killed and reported, never left to freeze. Run **`/subagents`** to list agents/config and **`/subagents doctor`** for a live self-audit (this is the check that never passed before). Tune via `PI_SUBAGENT_IDLE_MS` / `_TIMEOUT_MS` / `_MAX_DEPTH` / `_MAX_CONCURRENCY`.
  - **Watchdog budgets (idle + wall).** Defaults: idle 5 min, wall 60 min. A slow-by-design agent overrides both in its own frontmatter (`wall_ms:`/`idle_ms:`, ms), which wins over the env default (e.g. `agents/deep.md` sets 40 min / 10 min). See `docs/design/subagents-extension.md`.
- **Running subagents show in a pinned tracker** above the editor (status glyph, agent+model, live turns/tokens/cost, elapsed; auto-clears after a TTL). See `docs/design/subagent-pin-tracker.md` for the full mechanism.
- **Skills still written for the old `Agent` tool** (`subagent_type=fanout|review|deep`, Explore/Plan) do NOT map 1:1: use the `subagent` tool with `agent=fanout|review|deep` instead. The `Explore`/`Plan` tools are not provided.

## Hard-won gotchas


- **Kit is strict v2** (`schemaVersion: "2"`). The July 2026 strict grammar uses `permissions` (not `caps`), `setup` (not `commands`), `agentInstructions` (not `sandbox.aiFilename` + `agentContext`), and a list-valued `sandbox.entrypoint`. Credentials remain a `credentials[]` list of `service` + `apiKey` (name/proxyManaged/inject[]). The per-credential `service:` is required.
- **The proxy is TLS-intercepting.** CA trust comes from the kit `setup.install` command + `NODE_EXTRA_CA_CERTS`. Egress is allowed only to `permissions.network.allow` in `spec.yaml`: a new external host = add it there + recreate. A domain the proxy injects a credential into (`apiKey.inject[].domain`) must ALSO be allowed there.
- **The DHI base is minimal:** no `useradd` (append to `/etc/passwd`), `/usr/local/bin` may not exist (`mkdir -p`), no `gzip`/`curl`/`fd`/`hostname` by default (apt-install, or bake the static binary like ruff/fd do).
- **Clickable links need `jq`.** sbx injects its OWN `/usr/local/bin/xdg-open` (we don't ship it), which POSTs to `gateway.docker.internal:3128/_sbx/browser-open` so the HOST opens the URL. It builds that JSON with `jq -nc`, so with no `jq` it dies there and just prints the URL: that was the entire "links never work" bug. `jq`/`procps`/`file` are installed and `BROWSER=xdg-open` is set. Check: `xdg-open https://example.com`.
- **Stalled model streams:** pi has no client read timeout, so a dead SSE stream spins "working…" forever. `status.ts`'s watchdog auto-cancels a turn with no output for 3 min; otherwise `Esc`. Diagnose a hung sandbox with `ps` (idle CPU + no child process = network wait, not compute).
- **Personal context mounts RW at its host path, always.** `~/.local/share/pix/context` (skills + standing `AGENTS.md` + personal `output-styles/`) is an extra sbx workspace, so a session edits the user's real files and the dir can be a git repo. Two rules, one bug each: mount the context ROOT (mounting `skills/` hid `AGENTS.md`), and mount it UNCONDITIONALLY, creating it if absent (gating on "has entries" made the first skill unauthorable in-sandbox). So the MOUNT set (`MountDirs`) is NOT the SKILL set (`LiveSkillDirs`): pi gets `--skill <context>/skills`, sbx gets `<context>`. `skills/` is live (`/reload`); `AGENTS.md` is inlined into a kit at launch, so it lands NEXT sandbox.
- **Scrollback:** in `regular` TUI mode pi renders into the MAIN buffer and full-redraws snap the terminal to the bottom, so you can't stay scrolled up while output streams (not fixable from an extension). `settings.json` therefore defaults to pi 0.84's `tuiMode: "fullscreen"` (alt-screen, app-owned scroll region, docked editor); `/settings` toggles it live.
- **Detached subagent children MUST be reaped.** `detached:true` lets a watchdog signal the whole group, but the group outlives this process while the watchdogs (`setTimeout`s) die with it: anything still running at exit is an uncapped orphan, the "CPU climbs after a long session" leak. `subagents.ts` drains `LIVE_CHILD_PGIDS` on `session_shutdown` + `process.on("exit")`; keep the register/deregister pair if you touch the spawn path (`tests/subagent-child-reaper.test.mjs`).
- **Compaction continuation:** `extensions/compaction-continuation.ts` queues one private follow-up after threshold compaction only when output hit its token limit or a todo remains `in-progress`; manual compaction, retries, completed plans, and merely `not-started` work stay quiet. `scripts/patches/apply-todo-durable-clear.mjs` fixes `pi-manage-todo-list@0.4.0`: `/todos` and Alt+T toggle, `hide|show` is explicit, visibility persists, and clear emits canonical `pi-stack-todo-cleared` while readers still accept legacy `pix-todo-cleared`.
- **Full-auto:** no permission prompts: the sandbox isolation is the safety boundary.
- **MCP runs through sbx's LOCAL data-plane gateway**: always available, **no
  `SBX_MCP_URL`** (nightly serves remotes directly; `sbx mcp status` shows mode
  `local`). Every server comes from a pack (see the transport bullet below), one
  transport per sbx grammar. A **host command** (`command`, or `image` via `docker
  run`) registers as `sbx mcp add <name> --command … --args …` (**no `--env`**) and
  runs on the HOST as a daemon subprocess; when it declares `env_keys` the
  registered command is `op run --no-masking --env-file=~/.config/pix/op-refs.env
  -- <declared argv>`, resolving op:// refs at spawn (op-refs.env is the single
  mechanism; nothing stored in the registration or the VM). A **`manifest`** server
  registers `--local --url <manifest>`, creds Docker-side.
  **Remote** servers are registered by URL:
  `pix mcp add <name> --url <url>`, then `pix mcp auth <name>` for the
  hosted-control-plane OAuth (`mcp.McpCatalog` is a small lookup table of
  endpoints pix already knows, so those names need no `--url`). The CLI is
  three verbs, `add`/`ls`/`auth`: `register` (a distinction only the
  implementation cared about), `bundle` (three hardcoded SaaS vendors) and
  `load` (live-attach) were DELETED. **Every configured MCP server, and every
  active or transient pack integration, is emitted as `--static-mcp <name>` at
  sandbox CREATE** (`--mcp` is gone; sbx rejects it). Registering a server
  (`sbx mcp add`) only makes it known to the gateway; a session sees its tools
  only once it was preloaded at create. Servers come from
  the `mcp` list in `~/.config/pix/config.toml` (via `pix config get
  mcp`, which also drives `serve`/`mcp-register`/`doctor`/`pull-models`).
  A RUNNING sandbox catches up by being recreated: `pix rm BOX && pix run`
  re-sends the full `--static-mcp` set. There is no live-attach and no receipt
  store (U04e deleted it: "pix loaded this once" is not the state of a live
  session, yet `status`/`doctor` rendered it as `attached`). `doctor` reports more
  than registration now: declared-by-a-pack, command-resolves-on-PATH, and the
  pack's `probe` run through the SAME `op run` wrapper the gateway uses. Adding a
  server is a `pack.toml` edit, never a `pix-host` subcommand: `pix-host mcp
  --list` is permanently empty and `pix-host mcp <name>` serves nothing.
  - **Do NOT** hand-bake `url`/`command` entries into `mcp.json` pointing at
    `host.docker.internal`: that's a non-native bypass (and a `command` server hits
    pi's stdio client, which speaks newline-delimited JSON). Register with `sbx mcp
    add` instead. Public `mcp.json` has no servers and a problems-only footer; Docker injects the gateway entry.
  - Plain host services that are NOT MCP (`memory`; plus host-only service daemons
    a pack points at via a `[[proxy]]` wrapper, e.g. the snow exec proxy) are
    different: the sandbox reaches them directly over `host.docker.internal` (kit
    allowlist) via a wrapper/extension. `memory` runs under `make serve`; a pack's
    host daemon ships its own installer.
- **HOST = Go, SANDBOX = TypeScript (hard convention).** Everything that runs on
  the host is one compiled Go binary, `services/host/` → `pix-host` (subcommands
  per service). Everything that runs *inside* the sandbox (pi extensions in
  `extensions/`, in-box MCP) is TypeScript. Rationale: a single static binary is
  saner to ship, and decisively: a Node/Python interpreter that listens on a
  socket and **spawns a child process from network input is backdoor-shaped and
  trips endpoint security / EDR**. A compiled Go binary doing the same work runs
  unflagged. So when you add a host service,
  add a subcommand to `pix-host`, don't write another `node …/server.ts`.
- **Pix ships NO general/vendor MCP servers (exception: uat-mcp).** Every server comes
  from the active pack's `pack.toml`: an `[[integrations]]` stanza with **exactly
  one** transport (`command` host binary, `image` container, `manifest` OCI, `url`
  remote), `env`/`env_keys` for credential NAMES, optional `probe` for health.
  No transport is refused at LOAD; a `command` off PATH is refused at register; a
  requested name no active pack declares is an error, not a skip. `op run
  --env-file` wraps iff op-refs exists AND the server declares `env_keys`, so a
  credential-free server never shares fate with unrelated refs. Setup is
  declarative (`[[setup.require]]`/`[[setup.apply]]`), so a pack can never call a
  deleted verb: it never names one. The `gworkspace` and `slack` verbs are deleted,
  as are `mcp.GogHardenedArgv` and `google_workspace_account`. Google Workspace is
  just a pack-declared `command` server now: `docs/gworkspace.md`.
  - The precise exception is `uat-mcp`: it is ephemeral, dev-only, launcher-created for UAT, and closed. It is not a vendor integration, and it is never returned by `pix-host mcp --list`.
- **Private packs + host/container integrations (company-specific).** Open-core
  boundary: nothing company-specific is in the public repo, and **no `pix-host`
  recompile is ever needed.** Private context ships three ways: a **pack**
  (git-backed, runtime, no build: private `skills/`, `knowledge/`, `[[proxy]]`
  wrappers, and a root `capabilities.json` that mounts over
  `~/.pi/agent/capabilities.json`; `pix pack use <path>` activates it, see
  `docs/design/packs.md`); a **container MCP integration** (a host-executing
  server as an OCI image + `server.json`, referenced by `[[integrations]]
  manifest = "<url>"`, registered via `sbx mcp add <name> --local --url
  <manifest>` and run on the HOST by the gateway, creds provided Docker-side);
  or a **host-only service** (needs a browser/OAuth or host-cached creds: a
  standalone daemon + installer, with a thin in-sandbox `[[proxy]]` wrapper).
  Reference implementations stay private and separate.
  - Never reference a private file from a committed one: the public tree has
    none. `scripts/check-open-core.sh` (CI) fails if a company-specific file or
    internal marker is ever tracked.
  - **Company config/data has a home, and it is never the public repo.**
    Per-user or company-specific *data* (channel lists, customer names, tier
    rules, thresholds) goes in **pi memory** (`remember`, tagged) or a **pack**.
    Do NOT write it into a file in this tree, not even a scratch `*.yaml`: it
    would leak the hierarchy into the public image and trip the open-core guard.
- **Vendored renderer patch (`scripts/patches/`).** pi-tui's main-screen `doRender()` jitters the editor + powerbar while streaming (no viewport re-anchor on a bottom-anchored shrink); no extension fixes it, so the Dockerfile runs `apply-tui-bottom-pin.mjs` over the installed renderer. **Idempotent + non-fatal**: it warns and leaves the file unpatched if a pi version moves its anchor, so re-verify on every pi bump (step 4 above). Root cause, the scoped-full-render rationale, and tests: `docs/upstream/tui-bottom-pin.md`.

## Toolchain in the image

node 25 · npm · git · **gh** (HTTPS token via sbx proxy: use for PRs, not SSH) ·
ripgrep · **fd** · ruff · clangd · pyright · typescript-language-server ·
**Go** (`/usr/local/go`, pinned via `GO_VERSION` to match `services/host/go.mod`;
`GOTOOLCHAIN=local` so builds never fetch a toolchain: bump both together) ·
**chromium** + **agent-browser** (localhost QA) · python3 · build-essential.

Go is baked so you can build + test the host binary (`services/host` →
`pix-host`) from inside a sandbox when hacking on pix itself: `cd
services/host && go build ./... && go test ./...`. HOST code still only ships to
the host as a compiled binary; the toolchain in the image is a dev convenience.
