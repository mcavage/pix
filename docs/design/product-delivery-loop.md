# One product-delivery loop

The current product process is specified in [thinner product delivery](thinner-product-delivery.md).
PR/FAQ, PRD and architecture agreement precede implementation. One owner carries
product judgment and integration; workers and specialist challenges are optional
for ready units and concrete uncertainties. `plan`, `build` and `ship` share the
agreement and evidence rather than creating separate crews.

The integrated product receives executed journey evidence and independent review.
Material changes require affected checks and focused review; nonblocking findings
retain explicit dispositions. Local artifact, green PR and deployed release are
distinct claims. The following runtime boundaries remain unchanged.

The existing subagent runtime is a process/usage boundary, not a product state
machine. `max_turns` is a prompt hint, while idle/wall limits are executable.
Compaction continuation uses durable in-progress todos or a length stop; it is not
proof that all product criteria were satisfied. Files under `.pi-agent/deliver/`
record progress and evidence. Do not claim enforcement for prose alone.

Failed child results retain observed models, elapsed time and usage in the parent
text as well as structured details. Partial source is preserved and inspected;
neither failure nor successful exit proves candidate correctness. A budget refusal
must remain distinct from actual charged spend, and unknown usage is not zero.

Memory project lookup uses argument-vector Git execution so workspace names remain
literal. Recall remains append-only to preserve prefix caching; capture remains
explicit by default. Neither change introduces a second inference router or rate table.

Validation distinguishes three levels: packaging checks establish reachable
references; scripted child/Gateway tests establish runtime behavior; a live,
independently graded product run establishes model adherence. Passing the first two
must not be presented as proof of the third or superiority over native agents.
