# Pix memory service

An independent Go module implementing Streamable HTTP MCP at `/mcp` and a health
endpoint at `/healthz`. It uses one SQLite store and does not depend on the launcher
module. Pix setup runs it as one authenticated, loopback-published Docker container
per `PIX_HOME`; the agent reaches it through the sbx MCP Gateway.

See [the memory guide](../../docs/memory.md) for behavior and
[the architecture](../../docs/design/pix-v2-architecture.md) for deployment.

## Code

- `store/`: schema, migration, recall, deduplication, embedding, capture, snapshots.
- `server/`: MCP handlers, tool annotations, authentication, and health endpoint.
- `cmd/pix-memory/`: environment configuration and service entrypoint.

The tools are `memory_recall`, `memory_remember`, `memory_forget`, `memory_observe`,
`memory_stats`, `memory_status`, `memory_snapshot`, and `memory_restore`. Capture
is explicit by default. Every caller, including the Pi slash commands and recall
hooks, uses these tools rather than a second protocol.

## Configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `MEMORY_BIND` | `0.0.0.0` | Listen address inside the container |
| `MEMORY_PORT` | `8080` | Listen port |
| `MEMORY_DATA_DIR` | `/data` | Persistent state |
| `MEMORY_DB` | `<data-dir>/memory.db` | SQLite path override |
| `MEMORY_AUTH_TOKEN_FILE` | `/data/auth.token` | Bearer token generated by Pix setup |
| `OLLAMA_HOST` | `http://127.0.0.1:11434` | Embedding/watcher endpoint; Pix supplies the container-reachable address |
| `MEMORY_EMBED_MODEL` | `nomic-embed-text` | Embedding model |
| `MEMORY_WATCHER_MODEL` | `qwen3.5:9b` | Opt-in extraction model |
| `MEMORY_CAPTURE_MODE` | `explicit` | `explicit` or `experimental-auto` |

Without an authentication token, `/mcp` refuses requests even if `/healthz`
answers. The token file is the production path; `MEMORY_AUTH_TOKEN` is a development
fallback. Do not bake either into an image or put a resolved token in an example.

## Build and verify

From this directory:

```bash
go build ./...
go test ./...
go vet ./...
```

From the repository root, `make build-memory` builds the image. For end-to-end
verification, `make load` assembles the matching Pix bundle, then use `pix setup`
and a real Gateway memory call in an isolated `PIX_HOME`. Test recall before
checking `memory_status.embed_healthy`; a process being live does not prove that
its embedding backend works. Snapshot/restore tests must use disposable data.
